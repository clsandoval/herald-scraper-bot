# Roadmap: Herald Reviews Scout

## Overview

This is a hard-pivot overhaul, not a greenfield build: a spammy auto-posting bot becomes
a quiet, on-demand Dota 2 match analyst. The journey starts by carving a clean, secret-safe
platform out of the `daimon` fork and proving the thinnest possible vertical slice — mention
the bot, it queries a real (tiny) database, it replies — before any ingestion robustness or
scoring intelligence exists. From there we deepen: real OpenDota→Stratz ingestion running on
a schedule with retry/backoff and pruning, then the `herald-replay-quality` skill so replies
carry real domain judgment instead of raw rows, then the richer data fields (per-player,
net-worth-lead arrays) that better scoring depends on, and finally concurrency/safety hardening
on the Discord side. Each phase after the first ships something a human can observe end-to-end;
nothing is "half of a layer."

## Phases

**Phase Numbering:**
- Integer phases (1, 2, 3): Planned milestone work
- Decimal phases (2.1, 2.2): Urgent insertions (marked with INSERTED)

Decimal phases appear between their surrounding integers in numeric order.

- [ ] **Phase 1: Clean Platform Skeleton** - Trimmed daimon fork deploys to Fly with Postgres/Alembic, secrets from env only, legacy bot code and leaked token gone
- [ ] **Phase 2: Thin End-to-End Slice** - Minimal match table, a tiny manual/seed ingest, and `@mention` → SQL tool → Discord reply all work together on real (if sparse) data
- [ ] **Phase 3: Real Ingestion Pipeline** - Scheduled OpenDota discovery → Stratz enrichment → dedupe/persist → prune runs unattended, storing only, with retry/backoff on outages
- [ ] **Phase 4: Replay-Quality Skill Integration** - The query agent ranks candidates using the productionized `herald-replay-quality` skill instead of raw filters
- [ ] **Phase 5: Rich Match Data** - Per-player stats and net-worth-lead arrays are captured and available to the skill for throw/comeback and troll-build detection
- [ ] **Phase 6: Concurrency & Reply Hardening** - Concurrent mentions are handled safely and shortlist replies are well-formed under Discord's message constraints

## Phase Details

### Phase 1: Clean Platform Skeleton
**Goal**: A trimmed, secret-safe fork of daimon deploys cleanly to Fly.io with Postgres attached and migrations running on release — no legacy Telegram/Lambda code, no hardcoded tokens.
**Mode:** mvp
**Depends on**: Nothing (first phase)
**Requirements**: PLAT-01, PLAT-02, PLAT-03, PLAT-04
**Success Criteria** (what must be TRUE):
  1. The repo contains only the trimmed daimon core (db/models/config/turn/skills), Discord adapter, and scheduler adapter — multi-tenant/MCP/Slack/billing/provisioning/OAuth code is absent
  2. `bot.py`, `lambda_function.py`, `database.py`, and any other legacy/dead files are removed from the repo
  3. The leaked Telegram bot token is revoked and no secret values exist in source (all read from env/Fly secrets)
  4. A deploy to Fly.io succeeds, the app boots against an attached Postgres instance, and Alembic migrations run automatically on release
**Plans**: 3 plans
  - [ ] 01-01-PLAN.md — Purge legacy code + scrub leaked token from git history + scaffold uv workspace / daimon-core
  - [ ] 01-02-PLAN.md — Minimal mention→pong Discord adapter, inert scheduler package, baseline migration, Dockerfile/fly.toml/entrypoint
  - [ ] 01-03-PLAN.md — Deploy to herald-scraper-bot-test: Fly Postgres + secrets + release migrations + live @bot→pong

### Phase 2: Thin End-to-End Slice
**Goal**: The full request path works end-to-end on real infrastructure — a human can `@mention` the bot in Discord and get a reply generated by an agent that queried a real Postgres table via SQL.
**Mode:** mvp
**Depends on**: Phase 1
**Requirements**: DATA-01, ING-03, QRY-01, QRY-02, QRY-04, DISC-01
**Success Criteria** (what must be TRUE):
  1. A minimal `matches` table (keyed by `match_id`, idempotent re-insert) exists via SQLAlchemy + Alembic migration
  2. A handful of Herald matches can be persisted into that table (seed script or minimal one-shot ingest) without duplicate rows on re-run
  3. `@mentioning` the bot with a plain question triggers the MA agent, which uses a read-only SQL tool to query the matches table
  4. The bot replies in-channel with at least one candidate match (ID/link + a reason), and never posts without being mentioned
**Plans**: TBD

### Phase 3: Real Ingestion Pipeline
**Goal**: Herald matches flow into the database continuously and unattended — discovered via OpenDota, enriched via Stratz, deduped, pruned — with no auto-posting anywhere in the loop.
**Mode:** mvp
**Depends on**: Phase 2
**Requirements**: DATA-02, ING-01, ING-02, ING-04, ING-05, ING-06
**Success Criteria** (what must be TRUE):
  1. The scheduler adapter runs an ingestion job on a recurring cadence that only writes to the DB — it never posts to Discord
  2. Each run polls OpenDota `/publicMatches`, filters to Herald rank tiers (10-15), and enriches each new match via Stratz GraphQL parsed detail
  3. Per-match summary fields (duration, total kills, radiant/dire win, patch, avg rank tier) are persisted, deduped by `match_id` so re-runs don't duplicate rows
  4. Matches older than the retention window (default 30 days, configurable) are pruned automatically
  5. A simulated OpenDota/Stratz error or outage is retried with backoff instead of crashing the ingestion job
**Plans**: TBD

### Phase 4: Replay-Quality Skill Integration
**Goal**: When asked for review-worthy matches, the agent's answer reflects Jenkins' actual taste (chaos, low bracket, absurd stat lines) via the productionized skill, not an ad-hoc SQL filter.
**Mode:** mvp
**Depends on**: Phase 3
**Requirements**: SKILL-01, QRY-03
**Success Criteria** (what must be TRUE):
  1. The `herald-replay-quality` skill (weighted 0-100 rubric) is available to the query agent as a bound skill, not just a design doc
  2. Asking the bot for review-worthy matches returns candidates scored and ordered by the skill's rubric, with the top firing signals visible in the reply's reasons
  3. Matches that don't clear the skill's scoring bar are excluded or ranked below matches that do, observably changing shortlist order versus a naive "recent Herald matches" query
**Plans**: TBD

### Phase 5: Rich Match Data
**Goal**: The stored data is deep enough for the skill to score the signals it actually needs (troll builds, feed lines, throws/comebacks) — not just summary-level facts.
**Mode:** mvp
**Depends on**: Phase 4
**Requirements**: DATA-03, DATA-04, DATA-05
**Success Criteria** (what must be TRUE):
  1. Per-player rows exist for each ingested match: hero_id, K/D/A, GPM/XPM, net worth, item list + counts, lane/role, time-dead where available
  2. Each match has a persisted net-worth-lead array (from Stratz) usable for throw/comeback detection
  3. Re-running the skill against the same matches now surfaces signals (troll item builds, feed lines, lead reversals) that were previously unavailable, visibly changing scores/reasons for at least one known match
  4. Only the fields the skill's signal ledger actually needs are persisted — no unused columns/tables added "just in case"
**Plans**: TBD

### Phase 6: Concurrency & Reply Hardening
**Goal**: The bot behaves correctly under real Discord conditions — multiple people asking at once, long replies, message-size limits — so it's trustworthy enough for daily use in a live server.
**Mode:** mvp
**Depends on**: Phase 5
**Requirements**: DISC-02
**Success Criteria** (what must be TRUE):
  1. Two `@mentions` fired in quick succession (from different users or channels) both get correct, non-interleaved replies
  2. A ranked shortlist that would exceed Discord's 2000-character message limit is chunked/threaded correctly instead of failing or truncating silently
  3. A transient DB or agent error on one request doesn't wedge the bot for subsequent requests
